# 计算机网络

## TCP 三次握手
第一次：客户端发 SYN；第二次：服务端回 SYN+ACK；第三次：客户端回 ACK。目的是双方确认收发能力、同步初始序列号，防止历史连接干扰。

## TCP 四次挥手
主动方发 FIN，被动方回 ACK，被动方再发 FIN，主动方回 ACK 后等待 2MSL 关闭。因为 TCP 全双工，两个方向要分别关闭；TIME_WAIT 保证最后一个 ACK 可靠送达并让旧报文自然消亡。

## HTTP 与 HTTPS
HTTP 明文；HTTPS = HTTP + TLS，通过证书验证身份 + 非对称加密协商密钥 + 对称加密传输数据。中间人攻击的防护靠证书链校验。

## HTTP 状态码
200 成功；301/302 重定向；400 请求错误；401 未认证；403 无权限；404 不存在；429 限流；500 服务器错误；502 网关错误；503 服务不可用。

## GET 与 POST
GET 用于查询、参数在 URL、可缓存；POST 用于提交、参数在 body、不可缓存。语义上 GET 要幂等，POST 不要求。

## DNS 解析过程
浏览器缓存 → 系统 hosts → 本地 DNS 缓存 → 递归查询根/顶级/权威 DNS 服务器，返回 IP 后浏览器发起 TCP 连接。

## 浏览器输入 URL 后发生了什么
DNS 解析 → TCP 三次握手 → TLS 握手（HTTPS）→ 发送 HTTP 请求 → 服务器处理返回 → 浏览器解析渲染（HTML/CSS/JS）→ 建立连接池复用。

## TCP 与 UDP
TCP 面向连接、可靠、有序、有拥塞控制，适合文件传输/网页；UDP 无连接、不可靠但低延迟，适合直播、游戏、DNS。应用场景的选择本质是"可靠性 vs 实时性"的取舍。

## HTTP/1.1 与 HTTP/2
HTTP/2 在一条 TCP 连接上多路复用多个请求、HPACK 头部压缩、二进制分帧、服务端推送；解决应用层队头阻塞，但 TCP 层仍有队头阻塞，需 HTTP/3（QUIC）进一步解决。

## Cookie、Session 与 Token
Cookie 存在客户端、随请求携带；Session 存在服务端（内存/Redis），靠 cookie 里的 session id 关联；Token（如 JWT）无状态、服务端验签即可，适合分布式与跨域场景，注意过期与撤销问题。

## WebSocket
全双工长连接，服务端可主动推送，握手走 HTTP Upgrade；适合聊天、实时通知、协同编辑；HTTP 是请求-响应模式，轮询延迟高且浪费。

## 跨域与 CORS
浏览器同源策略限制跨域请求；后端加 CORS 响应头（Access-Control-Allow-Origin）放行，预检请求 OPTIONS 处理自定义头；生产常用反向代理同源化，避免复杂 CORS 配置。

## TCP 粘包
发送方缓冲区合并或接收方一次读走多条消息导致粘包；解决：消息定长、分隔符、头部长度字段；应用层协议自己定义边界，不依赖 TCP 流边界。

## 接口变慢怎么排查
分层排查：客户端网络 → DNS → 连接建立 → 服务端入口耗时 → 数据库慢查询/外部依赖 → GC/线程池；链路加 trace id 定位到具体环节，再针对优化（缓存、索引、并发、限流）。
